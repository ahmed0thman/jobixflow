# Jobs — Platform Admin
URL/route: `https://jobixflow.com/platform/jobs` (list) · `/platform/jobs/{id}` (show) · `/jobs/{id}/chat` (per-job chat, note: **not** namespaced under `/platform`)
Purpose: Cross-company job monitoring, detail view, and per-job chat observation. The richest page mapped so far — full pricing/payment/vehicle/timeline detail lives here.

## Navigation path
Sidebar → "Jobs" (fifth item). Job detail reached via row "Show" action; chat reached via "Open Chat" link on the detail page or "Chat" in the row kebab menu.

## CRUD actions tested
- **Create**: No create action on this page for Platform Admin — consistent with `CLAUDE.md`/`ROL-003` ("platform admin does not create jobs").
- **Read**: List table (Job ID+date, Company, Type, Customer, Technician, Status, Priority, Amount, Actions) with search, a status dropdown, and 3 quick-filter chips. Full Show page has: Job Information (IDs for both dispatchers with their unique codes, company, technician, description, needs-key/needs-code flags, timestamps), itemized Pricing Details (see Issues — line items now, not just one price), Payment Details, Customer Details (**real customer phone number and email visible to Platform Admin**), Vehicle Details (VIN, brand, model, year, plate, engine number, color), and a Status Timeline showing every transition with actor name, unique ID, and role.
- **Update**: No inline edit found on the Show page or list for job fields — Platform Admin appears to be pure read + delete only for jobs, no edit.
- **Delete**: Row kebab has a "Delete" link (after a separator). Not tested — same live-data safety reasoning as Companies/Countries.

## Hidden / secondary UI elements
- **Row kebab (Actions column)** — opens: Show / Chat (labeled "show chat Chat") / — separator — / Delete. Tested on job 88126; the row-action pattern matches Companies' kebab style (not Countries' inline-link style — reinforces the Companies/Countries inconsistency noted in `countries.md`).
- **Status filter dropdown** — "All Status" plus 12 explicit values: New Job, Assigned to Company, Company Refused, Assigned to Technician, Technician Refused, Technician On The Way, Technician Arrived, Work In Progress, tech request code, company get code, Completed, Cancelled. See Issues re: how this compares to the canonical flow in `NEW-REQUIREMENTS.md §6`.
- **Quick-filter chips** — "All Jobs" / "High Priority" / "Today", **no counts shown** (e.g. not "High Priority (12)"), unlike the count-bearing chip style described in the old design-system notes (`CLAUDE.md` § Design system, `[FIG:Jobs]`). Confirmed functional: clicking "High Priority" correctly filtered the table (page count dropped from 151 pages to 53, every visible row showed "High" in the Priority column).
- **Search box** ("Search by job ID, company, customer, or type...") — confirmed functional but **not live/debounced**: typing "vehicle" produced no change until Enter was pressed, at which point the result set correctly narrowed (53 pages → 26 pages, combined with the still-active High Priority filter). Worth flagging for the reusable Filter component spec — designer should decide submit-on-Enter vs. live-filter as the canonical pattern.
- **On the Show page, "Open Chat"** navigates to `/jobs/{id}/chat` — note this route is **not** under `/platform/`, unlike every other Platform Admin page. Same underlying chat view is presumably shared across roles (URL doesn't encode role).
- **Per-job chat page** has an "Internal" toggle button next to a "2 active chat" counter, suggesting multiple chat threads per job (at least a Platform Dispatcher ↔ Company Dispatcher thread, consistent with the allowed pairs in `CLAUDE.md`). Clicking "Internal" changed the toggle's active state but the visible thread content did not visibly change in this instance — inconclusive whether it actually switches threads or this job only has the one populated thread.
- **Chat composer is disabled** for Platform Admin: the message textbox and send button both render with `disabled` — correctly implements `ROL-004` (read-only chat for platform admin) with a visible (not just silently missing) composer.
- **Pricing Details block on Show page** contains **multiple itemized cost entries** (seen: two separate "Physical Key" line items on job 88126, $251.57 paid by "company" and $136.78 paid by "customer"), each with Cost Type, Cost, **Paid By**, Payment Status, and Notes — plus separate Estimate Price and Final Price fields. This is materially close to the new "Expenses" concept.

## States observed
- Empty state: Not observed (huge seed dataset, 151 pages of jobs).
- Loading state: Not observed.
- Error state: Not tested.
- Success/confirmation state: Not captured (no create/edit/delete completed).
- Disabled elements: Chat composer textbox and send button, disabled for Platform Admin (see above) — the one clear, deliberate disabled-with-reason pattern found so far in this audit.

## Validation & edge cases
Search-then-Enter behavior confirmed (see above). Did not test invalid/empty search, malformed job ID lookups, or boundary values on any numeric field.

## Permissions
Platform Admin: full cross-company read access to every job field including customer PII (real phone/email) and vehicle data, matching `CLAUDE.md` ("sees full job details incl. vehicle data & payments"). Chat is read-only (composer disabled, confirmed live). No create action (matches `ROL-003`). No edit action found for job fields themselves (only Delete, kebab-gated).

## Issues / inconsistencies / open questions
- **[FINDING] Live job status list has 12 distinct values that don't cleanly map to the canonical flow** confirmed in the 2026-08-17 follow-up (`NEW-REQUIREMENTS.md §6`: Call intake → Assigned → Accepted/Rejected → Confirmed by call → Started → Arrived → Completed/Cancelled). The live system has, at minimum: New Job, Assigned to Company, Company Refused, Assigned to Technician, Technician Refused, Technician On The Way, Technician Arrived, Work In Progress, tech request code, company get code, Completed, Cancelled — notably **two key-code states ("tech request code" / "company get code") are modeled as job statuses**, not as a separate Key Codes/Code Requests sub-flow, and there's no explicit "Confirmed by call" state visible. This needs reconciling with the developer before finalizing the status-pill/state-machine design — the abstract flow in the requirements doc and the live status enum are not obviously the same thing.
- **[FINDING] Pricing Details already has itemized cost lines with a "Paid By" field**, but the live value is **"company" or "customer"**, not **"technician" or "company"** as specified for the new Expenses feature (`FIN-W-013`: "tagged by the technician as paid-by-technician or paid-by-company at job close-out"). This is a live-system vs. requirement conflict, not just a gap — the existing "Paid By: customer" concept may be a different thing entirely (who ultimately bears the physical-key cost) from the new Expense's paid-by-technician/company distinction (who fronted the cash at close-out). Needs developer clarification before the Expenses screen is designed, flagged as new open question.
- **[FINDING] `Payment Method: "Payment Link"` already appears as a live value** on this job's Payment Details block, with a Transaction ID and Reference Number recorded. This suggests some backend/data-model support for payment links may already exist even though `CLAUDE.md`/`NEW-REQUIREMENTS.md §3.10` are explicit that **no UI has ever existed** for sending or completing one. Worth a developer check on whether this is live payment infrastructure or seed-data flavor text before assuming payment links are a from-scratch build.
- **[FINDING]** Customer's real phone number and email are shown in full on the Platform Admin's Job Show page. This does not violate any stated invariant (`COM-001`/`COM-002` only restrict the **technician's** and **customer's** view of each other's real numbers — Platform Admin isn't covered by those rules and `CLAUDE.md` explicitly says Platform Admin "sees full job details incl. vehicle data & payments"), but it's worth double-checking against the client if Platform Admin's visibility into raw customer PII is intended to stay unrestricted once the masked-calling system ships.
- **[FINDING] Quick-filter chips carry no counts**, contradicting the old design-system notes' "All Jobs (6)" style. Live system evidence should take precedence over the pre-deletion screenshot inference per `Rule 00 · R00-2`.
- **[OPEN]** Search-box behavior (submit-on-Enter, no live filter, no visible search button) should be confirmed as intentional vs. a missing button before being treated as the canonical pattern for the reusable Filter component.
- **[OPEN]** Whether the "Internal" chat toggle genuinely switches between multiple distinct threads, or this job simply only has one active thread, is unconfirmed — would need a job with more chat activity to verify.
- Did not test Delete (blocked/avoided for the same live-data reasons as other modules) — post-delete state, confirmation dialog content, and whether it reads "Archive" anywhere remain unverified here too, same open question as `AUD-002` elsewhere in this audit.
